## 1. 结论先行

**推荐方案 C：不动 `SortDialog`；在 ToolDock 的「排序编号」旁边加第三个大按键「轨道编号」，一键应用；两套编号作为两个独立字段并存；画布显示交给「编号显示组」扩展成的三态 tab。**

一句话理由：**轨道编号是零参数操作，和需要容差滑杆 + 131 行偏移量的空间排序根本不是同一种交互**（`src/lib/tracksort.ts:95-103` 明确论证了"轨道内部没有行的概念，不该有容差滑杆"），塞进同一个 tab 会让其中一边空着；同时两套编号**必须并存**，因为 `Box.index` 是单字段（`src/types.ts:24`），`useStore.applySort` 会把整列覆盖成 `null`（`src/store/useStore.ts:385`），不新增字段就等于 silently 毁掉用户调好的空间编号。

## 3. 六个维度逐条分析

### 3.1 两种编号的关系：互斥还是并存？

**结论：并存（两个独立字段），但"哪个编号算主编号"要显式化。**

理由：

1. **不复用字段就等于毁数据。** `applySort` 的写法是 `boxes.map(b => ({...b, index: res.order.get(b.id) ?? null}))`（`useStore.ts:385`）—— 全列覆盖。如果第二套编号也写 `index`，用户调了一个下午的逐行偏移量（`SortDialog.tsx:97-110`，最多 131 行）会被一次点击清空，而且没有任何提示。这不是交互选择问题，是数据丢失。
2. **两个编号回答的是不同问题，都有人要。** 空间编号 = 整幅辊面的阅读顺序（1..896，"第几行第几个"）；轨道编号 = 列内位置（1..64，"第 5 列第 3 根"）。用户原话就是"两种编号体系并存"。
3. **算两份没有成本。** 两个函数都是 O(n log n) 纯函数，896 个点跑两遍是微秒级。`check-tracksort.ts:58-59` 已经验证了"每个框上两套编号都拿得到"。
4. **导出可以加法式扩展。** `buildExport` 已经是"有条件才写字段"的模式（`jsonio.ts:71,90`），加第二个条件字段是同一个套路，老消费者忽略未知字段即可，完全向后兼容。

**但有一个约束：`index` 的语义不能改，必须仍然是空间编号。** 证据是 `scripts/check-roundtrip.ts:20` 按 `index` 建 Map——per-track 编号在 18 条轨道里会重名 18 次（每条都有 1..64），塞进 `index` 会让这个 Map 互相覆盖，往返校验直接失败。所以：

- `index` = 排序编号（语义不变，`types.ts:10-11` 的注释继续有效）
- `track_index` = 轨道内编号（新字段，新增）
- 导出时两个字段都写（各自有条件守卫）

"主编号"只影响一件事：**导出数组的顺序**。建议规则（三行就能写清）：

```
排序键 = 当前激活体系的值；该体系没编号时退回另一套；两套都没有就保持文件原序
```

默认激活 `'spatial'`，所以**不碰新功能的用户，导出结果和今天逐字节一致**。这条很重要，是"新增功能不改变现有行为"的底线。

### 3.2 和现有 UI 的一致性：该复用哪个模式？

要区分两件事，它们对应不同模式：

| 事情 | 性质 | 该复用的模式 |
| --- | --- | --- |
| 「应用轨道编号」这个动作 | 一次性操作，零参数 | **P5**（和「清除编号」一样的一键即时动作） |
| 「画布/面板上看哪套编号」 | 持久状态，随时可切 | **P1**（分组 tab + 滑动指示器，和工具组/编号显示组同款） |

具体依据：

- **复用 P1 是零成本的**：`useTabIndicator`（`ToolDock.tsx:20-36`）靠 `c.querySelector('.dock-tab.active')` 测量，`LABEL_TABS` 从 2 项改成 3 项就行，钩子、CSS（`.dock-tab-ind` 的 `transform`/`width` 过渡，`styles.css:878-893`）一行不用改。这是仓库里唯一一个"为 N 态设计"的控件。
- **不该复用 P2（弹窗）做切换**：`SortDialog` 是一次性操作界面（打开→调参→应用→关闭，`sortOpen` 关闭即卸载，`SortDialog.tsx:50`），持久状态放弹窗里是错的容器。
- **P3（chip）不适合**：chip 表达的是"多选一筛选 / 可取消"，编号体系是"单选一模式"，而且 chip 在左侧面板里，离画布远。
- **P4（顶栏）不适合放编号**：见 §3.6。

### 3.3 两种编号的参数差异：tab 里放一堆用不上的控件会很怪

**结论：差异极大，这是判「方案 B 死刑」的主要技术理由。**

> 后续（轨道编号补上参数后）：见本节末尾的说明。

| | 排序编号 | 轨道编号 |
| --- | --- | --- |
| 参数 | 行容差 20~160px（`SortDialog.tsx`） | 分列容差 2~60px（`RecomputeTracksDialog.tsx`） |
| 微调 | 每行偏移量可编辑，最多 131 行，带「重算自动值」（`SortDialog.tsx`） | 每列偏移量可编辑，带「重算自动值」（`RecomputeTracksDialog.tsx`） |
| 预览 | 实时行数/空行/未落入任何行的散点告警 | 实时列数/空列/散点告警 + 轨道号会变的点位 |
| 组件状态 | `tolerance` + `edited`，且容差变化要重置 `edited` | 同左 |
| 代码量 | 弹窗里约一半行数在渲染控件 | 同左（多一个变化明细列表） |

具体问题：

1. **tab 2 的内容会只剩一段文字和一个按钮**。`.offsets` 那块（含 `OverlayScrollbars` 初始化，`SortDialog.tsx:23-36`）是整个弹窗最重的部分，在 tab 2 下完全是死代码。用户看到的是一个"空了一半"的弹窗，第一反应是"坏了"。
2. **组件状态会互相污染**。`tolerance`/`edited` 是 `SortDialog` 的局部 state。做成 tab 后，切走再切回来：要么丢掉用户调好的 131 行偏移量（不可接受），要么留着（那 tab 2 打开时背后藏着一堆看不见的状态，改容差时的 `useEffect` 重置还会在用户看不见的地方生效）。
3. **两个动作的语义不对称**。空间排序是"调参→预览→应用"；轨道编号是"想清楚就直接Apply"。tab 暗示两者是同构的，会误导用户去轨道 tab 里找不存在的滑杆。
4. **弹窗是错容器**（见 §3.2）：编号体系是持久状态，模态框装持久状态。

> **后续**：轨道编号后来补上了分列容差（2~60px，比行容差小很多）和每列偏移量
> （`tracksort.ts` 的 `offsets` + `RecomputeTracksDialog.tsx`），两个弹窗已经同构，
> 上面第 1、3 条理由随之失效；第 2、4 条（状态污染、弹窗装持久状态）依然成立。

**什么情况下 tab 方案会变合理**：如果轨道编号将来真的有参数。`tracksort.ts` 已经预留了两个——`direction: 'desc'`（从下到上编）和 `numbering: 'global'`。一旦产品决定把"编号方向"暴露给用户，轨道编号就从"一键"变成"二选一+应用"，这时候它在形态上才和空间排序对齐，tab 方案值得重新评估。**但即使到那时，我也建议用独立弹窗而不是 tab**，理由同上。

### 3.4 清除 / 重算的入口

现在 Dock 有两个大按键：`排序编号`（打开弹窗）和 `清除编号`（`ToolDock.tsx:61-79`，`disabled={!hasIndex}`，`hasIndex = boxes.some(b => b.index != null)`，`ToolDock.tsx:51`）。

加了第二套编号之后：

| 问题 | 建议 |
| --- | --- |
| 「清除编号」清哪套？ | **两套都清**。只清激活的那套，用户下次切过去会看到一串过期数字，比没有更糟。`hasIndex` 判断改成 `index != null \|\| trackIndex != null` |
| 需要分体系清除吗？ | **不需要**。两套都是可一键重算的，清掉重按比"只清一套"更容易理解。少一个入口少一个学习成本 |
| 「清除编号」的文案 | 保持四个字不变，但 tooltip 要写全："清除空间编号与轨道编号（可撤销）" |
| `SortDialog` 底部的「清除现有编号」（`SortDialog.tsx:116-118`） | 保留（在"我准备重新编号"的语境里很顺），但文案改成「清除全部编号」，否则用户会以为它只清空间编号。它和 Dock 那个按键功能重复，这是今天就存在的冗余，不建议在这次改动里删 |
| 「重算」入口 | **不新增按钮**。重算就是再按一次对应的编号按键（幂等）。但需要一个"编号已过期"的提示，见 §7.1 |
| Dock 会有几个键 | 3 个大按键（排序编号 / 轨道编号 / 清除编号）+ 2 组 tab。`dock-action` 是 34×34（`styles.css:834-856`），三个约 110px，整条 Dock 约 300px。2048 宽的画布没问题，但窄窗口要用户实际点一下看会不会挤（按 AGENTS.md，我不主动跑 UI 测试） |

### 3.5 画布上显示哪个编号？

**结论：把「编号显示组」从两态扩成三态，并引入一个 `numbering` 状态表示"哪套编号是当前激活的"。**

三态定义：

| tab | 图标 | 画布文字 | 说明 |
| --- | --- | --- | --- |
| 显示 ID | `Eye`（不变） | `String(b.studId)` | 今天的行为，默认值 |
| 显示编号 | `Hash`（新） | 激活体系的值 | 空间→`123`；轨道→`5-3`（`track_id-编号`） |
| 隐藏 | `EyeOff`（不变） | 不画 | 今天的行为 |

配套规则：

1. **`LabelMode` 类型扩展**：`'on' | 'off'`（`types.ts:38`）→ `'on' | 'number' | 'off'`。`AnnotationStage.tsx:467` 的 `labelMode !== 'off'` 判断不用改，`483` 行的 `text` 要按模式取值。
2. **中间 tab 的禁用条件**：激活体系一套编号都没有时禁用，tooltip 写"还没有编号，先用 Dock 上的「排序编号」/「轨道编号」"。否则用户点了发现画布啥也没变，会以为功能坏了。
3. **应用编号后自动切到「显示编号」**，但**仅当当前是 `'on'`**（也就是标签正可见）。如果用户主动关了标签（`'off'`），不要强行打开。这条规则很重要：否则最常见的首次流程是"点了轨道编号 → 画布什么都没变 → 以为没生效"。
4. **轨道模式的文字必须是 `5-3` 而不是 `3`**。per-track 编号在 18 条轨道里重名，单独一个 `3` 在缩放到单列、或者截图给别人的时候无法解读。框颜色确实已经编码了 track（`colors.ts:12-18`），但颜色不能复制粘贴。三四个字符在 138×45 的框里完全放得下（字号封顶 12px 屏幕像素，保底 8px，`AnnotationStage.tsx:37,470-475`）。如果实测太挤，退成 `3` 是可选优化，不是默认。
5. **首次切换要有人提示**。今天画布上是 studId，切到「显示编号」后所有数字变成 1..896 或 `5-3`，用户很可能以为数据被改了。toast 文案要写明"画布现在显示的是排序编号，原 stud ID 可在列表/属性面板查看"。
6. **列表和面板怎么跟**：
   - 属性面板「编号」行（`PropertiesPanel.tsx:136-139`）：显示激活体系的值；两套都存在时加一行「另一套编号」显示另一套。这是全应用最贵的 3 行代码，但能把"两套并存"这件事说清楚。
   - 列表（`BoxList.tsx`）：**v1 不加列**。面板总宽 264px（`styles.css:45`），现有列已经占满：`.id` 42px（`styles.css:506-512`）+ `.track` 26px（`487-496`）+ `.dim` 52px（`529-534`）+ 3 个 gap×8 + padding 20 = 164px，`.coord` 只剩 100px。再塞一个 44px 的编号列，坐标会被压到 ~56px 开始折行。编号信息已经在 tooltip 里了（`BoxList.tsx:263-270`），v1 只需把 tooltip 扩成"两套都显示"。
   - 可选 v3：激活编号模式时把 `.id` 列的内容从 `#studId` 换成当前编号（列宽不变，零布局成本）。代价是列表里看不到 stud ID 了，是个真实的回退，所以不做默认。

### 3.6 发现性

用户原话："收起那个位置特别难找，几乎没人能看到。" 所以新入口的原则是：**放在用户已经知道"编号在这"的地方，并且不新增任何需要发现的 affordance。**

- ✅ **Dock 的「排序编号」旁边**。用户要找编号功能，目光一定落在这个已经有 `ListOrdered` 图标的按键上。第三个按键和它并排，同一处、同一尺寸、同一无底色样式（`.dock-action`），学习成本接近零。
- ❌ **顶栏**（方案 A 的原始形态）。顶栏按仓库自己的逻辑是文件/视图/历史（`Toolbar.tsx:84-150` 四组：文件、缩放、撤销重做），编号是画布内容操作。放过去等于把"编号"从它唯一的家里搬走，还要用户去一个从没出现过编号的地方找。而且顶栏 `overflow-x: auto`（`styles.css:57`），窄屏本来就要横向滚。
- ❌ **任何折叠/二级菜单**。BoxList 的图例默认收起（`BoxList.tsx:53,148-150`）、HelpCard 默认收起（`HelpCard.tsx:66`）—— 这个仓库已经有太多"收起即消失"的东西，不要再加一个。

**可选的发现性助推**（建议做，但要知道它在做什么）：当用户已经应用过空间编号、但还没应用过轨道编号时，给「轨道编号」按键加 `.btn.attention` 呼吸高亮（`styles.css:137-157`，这个 pattern 今天用在"下一步该点哪个"上，`Toolbar.tsx:77-78`）。条件一满足就永久停止，不会变成长期噪音。如果觉得打扰，去掉也不影响主流程。

## 4. 歧义 (a) / (b) 的处理

用户说"给 track_id 排序"，至少两种解读：

### (a) 按轨道编号：每条轨道内部 1..N（「第 5 列第 3 根」）

**这就是要做的那一个。** 它是 `computeTrackSort` 的 `per-track` 模式（默认），零参数，`check-tracksort.ts:42-45` 已经校验了每条轨道内部恰好是 1..N。

**仓库内部证据（说明 (a) 才是这个代码库的自然概念）**：`BoxList.tsx:98-107` 的「轨道」排序键已经在做"按 track_id 分组，同列内按 bbox[1] 从上到下"—— 也就是说，**轨道编号就是把这个已经存在的列表视图固化成持久数字**。用户每天看列表都在看这个顺序。

### (b) 重排轨道号本身：把 track_id 规范化成按 X 从左到右连续的 0..17

**v1 不做，而且它在本数据上是个空操作。** 我实测了 `public/studs.json`：

| track_id | 0 | 1 | 2 | ... | 17 |
| --- | --- | --- | --- | --- | --- |
| 点数 | 48 | 16 | 32 | ... | 48 |
| 列轴线 meanX (px) | 200.8 | 330.6 | 364.5 | ... | 1869.8 |

track_id 已经是连续的 0..17，且 meanX 随 track_id **严格单调递增**。也就是说 `normalizeTrackIds`（`tracksort.ts:193-226`）在当前数据上跑出来的 remap 是恒等映射 —— 做了和没做一模一样。这不可能是用户想要的效果。

而且 (b) 的性质和 (a) 完全不同：

- (a) 是**新增一个字段**，不碰任何现有数据；(b) 是**改写一个已有字段** `track_id`。
- (b) 会**改变方框颜色**（`trackColor(track_id)`，`colors.ts:12-18`），视觉上像数据错乱。
- (b) 会**改变导出的 `track_id`**（`jsonio.ts:87`），下游消费者直接受影响。
- (b) 和已有的单框/批量改轨道号（`PropertiesPanel.tsx:44-73,176`）职责重叠，且**不幂等安全**：用户手工改过的轨道会被静默重排。

**建议**：如果将来确实需要（比如手工改过 track_id 之后出现了 0/3/99 这种断码），作为一个**独立的、明确标注破坏性的**入口「规范化轨道号」来做，弹窗里给出 `旧→新` 映射表 + 轴线重合告警（`normalizeTrackIds` 已经返回 `merged`，`tracksort.ts:214-219`），应用前必须能看清会改什么。绝不要把它折叠进"编号"家族里 —— 一个是加字段，一个是改字段，混在一起用户永远分不清自己刚才点了什么。

### 附：`global` 模式是个陷阱，v1 不要暴露

`computeTrackSort(boxes, { numbering: 'global' })` 会得到全局唯一的 1..896（按列首尾相接，`check-tracksort.ts:61-65`）。它看起来像空间编号的替代品，但**阅读顺序是列优先而不是行优先**，和 `computeSort` 的 1..896 是两个不同的排列。一旦暴露在 UI 上，一定有人以为"这才是真正的编号"然后拿它去覆盖 `index`。lib 里留着（给脚本用），UI 上不放。同理 `direction: 'desc'` 也不放。

## 7. 最容易忽略、但上线后会出问题的点

按危险程度排序。

### 7.1 编号过期（最容易被忽略，也最容易造成错误导出）

**现状就是坏的**：`updateBox` / `moveSelected` / `setTrackId` / `addBox` / `deleteSelected`（`useStore.ts:283-350`）**没有一个会碰 `index`**。所以今天用户拖个框、改个轨道号，导出 JSON 里的编号就是过期的一排数字，没有任何提示。加了第二套编号之后，这个问题的面翻倍，而且两套编号的过期条件还不一样：

- 空间编号：拖框（Y 变了）就过期；改 `track_id` **不过期**（空间编号不看 track）
- 轨道编号：拖框**或**改 `track_id` 都过期

**建议的最小实现**：store 里加一个 `dataStamp: number`，上面那批 action 各 `+1`；`applySort` / `applyTrackNumbering` 各自记下当时的 stamp；派生一个 `numberingStale` 布尔。UI 上在三处露一个极淡的提示（Dock 按键 tooltip、属性面板「编号」行旁边、状态栏），文案指向"再按一次对应的编号按键即可重算"。不需要自动重算 —— 自动重算会让"删一个框全部编号变了"，更吓人。

### 7.2 per-track 编号不全局唯一，任何把它当 key 的代码都会静默出错

18 条轨道各有 1..64。危险的具体位置：

- 下游消费者写 `studs.find(s => s.track_index === 3)` → 拿到 18 个里的第一个，错的
- 我们自己以后写任何"按编号查找"的逻辑 → 必须带 `track_id`
- `check-roundtrip.ts:20` 那种按编号建 Map 的写法 → 会互相覆盖（这是 §3.1 坚持 `index` 语义不变的主要原因）

缓解：所有 UI 展示一律 `track_id-编号`（画布、面板、tooltip），JSON 里 `track_id` 和 `track_index` 挨着写，文档里写明"唯一键是 `(track_id, track_index)`"。

### 7.3 「画布上显示编号」今天是完全不成立的，首次切换会被当成数据损坏

见 §2.3。切到「显示编号」后画布数字从 `1234` 变成 `287` 或 `4-11`，用户很可能以为框被重新编号了、原 ID 丢了。toast 必须解释，并且属性面板要同时显示 `studId` 和两套编号（`PropertiesPanel.tsx:133-139` 现在只有 ID 和编号两行）。

### 7.4 导出顺序与字段语义要分开决策

最容易踩的坑是"为了省事，让激活体系直接写进 `index`"。后果：`check-roundtrip.ts:20` 挂掉；老文件重新导入后 `index` 被解释成空间编号但实际是轨道编号，**静默错数据**。坚持 §3.1：`index` 永远=空间，`track_index` 永远=轨道，只有数组顺序跟着激活体系走。

### 7.5 三个按键之后 Dock 的宽度与遮挡

3×34 + 2 组 tab + 分隔 ≈ 300px，右下角还叠着缩略图（右侧 12px，`styles.css:795-805`）和左下角的 HelpCard。窄画布 / 低分辨率下要用户实际点一下。按 AGENTS.md，我不主动跑 UI 测试，这条列为交付后人工检查项。

### 7.6 和并发编辑的命名冲突

`src/lib/tracksort.ts` 正在被另一个进程写。`Box.trackIndex` / JSON `track_index` / store action 名字要尽快定并同步，否则 `types.ts`、`jsonio.ts`、`useStore.ts` 会双向覆盖。本文档 §5.1 给出建议命名。

### 7.7 `global` / `desc` 两个已实现但未暴露的选项

## 8. 分阶段实现建议

每个阶段都能独立交付、独立验证，且 Phase 1 之前用户行为零变化。

## 9. 备选方案是什么、什么情况下它更好

### 方案 A：在 Toolbar 里加按钮入口（点开弹窗/下拉）

**做法**：顶栏加一个图标按钮，点开一个下拉或新弹窗做轨道编号。

| | 评价 |
| --- | --- |
| 优点 | 顶栏常驻、位置符合"标准桌面软件"直觉；不占 Dock 宽度 |
| 缺点 | **违背仓库自己的分组逻辑**——顶栏四组分别是文件/缩放/撤销重做（`Toolbar.tsx:84-150`），编号是画布内容操作，今天就在 Dock 里。用户刚在 Dock 学会了「排序编号」，现在要去顶栏找「轨道编号」，两件事被拆到两个地方；顶栏 `overflow-x: auto`，窄屏要横滚；顶栏是纯图标 + 250ms 延迟 tooltip，发现性并不比 Dock 好 |
| 什么情况下更好 | 如果产品决定把「编号」整体上升为一级功能（比如以后还有第三、第四套编号），顶栏给一个带文字标签的「编号」按钮 + 下拉菜单列出所有编号体系，比在 Dock 里堆第四个大按键更合理。**那是功能数量变化导致的质变，不是这次的两个体系** |

### 方案 B：给 SortDialog 加 tab（空间排序 / 轨道排序）

**做法**：`SortDialog` 里做两个 tab，标题改「编号」。

| | 评价 |
| --- | --- |
| 优点 | 只有一个编号入口，用户不用分辨"该点哪个"；弹窗标题「编号」比「空间排序编号」更准确 |
| 缺点 | ① 参数严重不对称，tab 2 只剩一段文字 + 一个按钮，`.offsets`（`SortDialog.tsx:88-113`，含 OverlayScrollbars 生命周期）在 tab 2 下全是死代码，弹窗看起来像坏了；② `tolerance`/`edited` 局部 state 跨 tab 保留还是丢弃都是坑（`SortDialog.tsx:46-48` 的容差重置 effect 会在用户看不见的地方跑）；③ 弹窗装不了持久状态（`numbering`），而"画布显示哪套"必须是持久状态；④ 零参数操作被硬塞进"调参→预览→应用"的框架，多一次无意义的打开弹窗 |
| 什么情况下更好 | 轨道编号**真的有参数**的时候。`tracksort.ts` 已实现 `direction:'desc'`——一旦产品要把"从上到下 / 从下到上"暴露给用户，轨道编号就变成"二选一 + 应用"，和空间排序同构，tab 才顺眼。**但即使那时我也建议独立弹窗**（参数不同就该是不同的弹窗），tab 的唯一卖场是"入口只有一个" |

### 方案 C（推荐）：Dock 第三键 + 双字段并存 + 三态显示

见 §5。核心是**把"操作"和"状态"分开**：操作用 Dock 大按键（和现有两个编号键同构），状态用 tab 组（和现有两组 tab 同构），两边都复用仓库里已有的模式，不引入任何新的交互语言。

## 10. 开放问题（需要产品拍板）

1. **应用编号后自动切画布显示**（§3.5 规则 3）—— 建议"仅在 `labelMode==='on'` 时自动切"。如果用户明确反对自动切换，退化成 toast 里说明。
2. **`.btn.attention` 助推**（§3.6）—— 建议加，条件"已应用空间编号 && 未应用轨道编号"，满足后永久消失。
3. **轨道编号的画布文字格式** `5-3` vs `3` —— 建议 `5-3`（§3.5 规则 4）。
4. **导出数组顺序是否跟随激活体系** —— 建议跟随（§5.4）。如果想零风险，Phase 1 可以暂不接，保持永远按 `index` 排。
5. **删除框后编号跳号要不要自动重排** —— 建议不重排（§5.5），和 `index` 今天的行为一致。
